1. 为什么要做全双工测试？（核心背景与架构痛点）
像 MOSS-Live、GPT-4o Realtime 这类模型，最革命性的变化在于人机交互进入了‘全双工’：AI 在说话的同时耳朵全时开着，用户随时可以插话、纠正参数，甚至随口说‘嗯、对’，模型还能在后台异步调工具。这种模式给测试带来了全新的挑战，以前那种‘发一段语音、等文字出来、算个字错率’的单句测法彻底效。
• 1.1 话语权冲突与双通道解法打断必须快（≤300ms），但人随口附和‘嗯/对’又绝不能被打断。纯靠声学能量无法兼顾，必须采用‘声学快通道立即压麦静音 + 语义慢通道 150ms 决定是否恢复推流’的双通道决策架构。
• 1.2 隐藏硬件与管道缺陷 (AEC & Buffer)扬声器播放的声音被麦克风录回，模型误以为用户在插话而瞬间闭嘴，陷入抽搐式的静音死锁；打断后客户端未完全清理缓冲区，导致半个字破音残留在耳边。
• 1.3 语料防带坑门禁测试语料若带有爆音、削波破帧或咬字不清，会导致测试假阳性；必须涵盖川普、粤普、快语速及同音词对抗。

3. 为什么传统的单句录音测法行不通？（常见踩坑总结）
• 3.1 扬声器回音泄漏导致‘自己打断自己’ (AEC 缺陷)扬声器播放模型声音同时被麦克风录回，若 AEC 回声消除能力不足，模型误判定为用户在说话而瞬间闭嘴，导致一句话断成七八截，一直在那自我抽搐死锁。
• 3.2 管道残存音频溢出与瞬态爆音 (Buffer Leakage)打断后若前端仅停止拉流而未清空底层播放缓冲区，会漏出半个字的声音；若采用硬截断又会引入刺耳的瞬态爆音（click），必须采用‘立即静音 + 5~10ms 软淡出’标准。
• 3.3 假连接与无声死音自动化测试仅断言 ICE connected 极易出现网络连着但音频流中断（死音）的情况，必须通过 peerConnection.getStats() 提取真实音频能量（totalAudioEnergy > 0）。
• 3.4 文本逐字比对对生成式模型失效大模型重述内容很难做到字字不差，用传统逐字匹配判定断点接续会误报失败，必须升级为复旦 FDB 官方认可的‘打断不变性（Interruption Invariance 语义等价评分）’。

4. 必须守住的测试指标与合格线（核心 SLA）
4.1 打断刹车时延 (Barge-in Stop Latency) P95 ≤ 300ms 从麦克风声学起始点 t0 到扬声器最后可听帧 t1 的绝对时延。P50 ≤ 200ms，P95 ≤ 300ms，硬上限 ≤ 350ms。
4.2 管道残音能量与溢出 (Buffer Leakage) ≤ 1 帧 (<-45dBFS) 刹车点生效后，下行音频轨道不得出现 > -45dBFS 的有效可听帧，残音溢出 ≤ 1 帧 (≤ 20ms)。
4.3 思考留白误抢话率 (Premature Interruption Rate) ≤ 1.5% 业务容忍窗口标定为 2.5s，测试阶梯覆盖 0.5s ~ 3.0s（在 0.5s~2.5s 正常留白区间误抢话率 ≤ 1.5%；>2.5s 进入安全询问/超时交权边界）。
4.4 附和倾听精准度 (Backchannel Precision) ≥ 98.5% (全盘统一口径) 用户随口说‘嗯’、‘对’、‘好的’，模型判定为倾听信号并继续平稳讲完整句的成功率 ≥ 98.0%。
4.5 闲聊与旁人讨论误插话率 (False Barge-in Rate) 严格 0 次 / 0 字节 多人开会或旁边闲聊期间，模型下行推流无可听发射音频（0 有效音频能量帧），闲聊误接话率严格为 0 次。
4.6 突发定向唤醒时延与回忆率 ≤ 600ms / 召回 ≥ 90% 多人热聊中突发点名提问，从喊话结束到首个下行音频包到达在 ≤ 600ms 内，且对刚才讨论争议焦点的召回率 ≥ 90.0%。
4.7 回声防自激能力 (AEC Leakage Tolerance) 0.0% 自激 在扬声器播放自身声音并以 50% 增益反灌录音端时，模型自激误打断发生率严格等于 0.0%，回声下正常平稳播报。
4.8 声学物理无爆音门禁 Jump ≤ 8000 / 削波 0% 16-bit PCM 单步相邻样点一阶差分突变 Jump ≤ 8,000，幅值满幅削波率严格等于 0.00%，直流偏置控制在 < 5.0。

5. 主流评测方案与工具深度调研体系（8 大前沿方案全景）
本章节系统性聚合了学术界与工业界现行的 8 大主流全双工评测方案与前沿工具，解耦为结构化速查卡片，并明确我们系统的具体吸收落地方式：
5.1 主流方案与工具结构化卡片速查
【方案 1】 MOSS-Live 官方 FDB 基准 (Full-Duplex Benchmark v1 ~ v3)核心定位：复旦大学 / 模思智能官方全双工模型基准。核心测什么：模型侧核心三指标：思考停顿等待率、附和识别率、打断响应率、打断后接续率、无关语音拒识率。我们怎么用：直接采纳其五大拟人指标口径作为体验放行门禁；用 FDB 的‘打断不变性’评分替代逐字比对；分层复用：模型侧用 FDB 离线批跑，系统工程侧用 WebRTC E2E 自建环境。
【方案 2】 Instruct-FD 音素级强制对齐注水基准 (Forced Alignment Benchmark)核心定位：全双工时序强制音素对齐评测基准。核心测什么：通过 MFA (Montreal Forced Aligner) 将打断标记 <barge-in> 精确绑定在特定词汇乃至特定音素上（如辅音 /t/ 发音后 30ms），评估模型在确凿毫秒点下的响应行为。我们怎么用：全面革新过去‘在第几秒’粗暴注入音频的不可靠做法，实现跨模型横向比对 100% 确定性可重复。
【方案 3】 CoDeTT & DualTurn 对话轮转基准核心定位：清华大学与学术界标准双通道对话轮转评测库。核心测什么：采用真实人-人双轨录音回放，评估系统对 EOT (有效发言结束)、Hold (思考留白) 与 Turn-shift 的识别 F1 分数。我们怎么用：将测试语料从单一脚本升级为‘双轨对话回放 + 四类事件标注’，利用上下文语义前瞻判定是否交出话轮，消除 98% 误抢答。
【方案 4】 FireRedChat 碰撞窗口与话权交叠分级模型核心定位：工业级全双工端到端交互与话权仲裁架构规范。核心测什么：科学定义交叠时间窗口：0~150ms 判定为无害自然交叠；150~250ms 判定为容忍决策缓冲；>250ms 判定为恶性抢话碰撞。我们怎么用：在评测大盘中引入‘碰撞窗口时长’与‘主动让步率 (Floor Yielding Ratio ≥ 98%)’硬门禁。
【方案 5】 LiveKit Agent Testbench (TestMu AI)核心定位：LiveKit 官方开源的 WebRTC 端到端实时测试套件。核心测什么：基于 WebRTC 的端到端突发音轨注入与弱网丢包模拟，检测 Agent 在 speech.started 时的反应与 KPI 指标。我们怎么用：全面吸纳其队列物理清空机制：一打断立刻调用 audio_source.clear_queue() 清空底层 JitterBuffer；将 getStats（收发字节、audioLevel、丢包率）做 1 秒级轮询监控告警。
【方案 6】 Full-Duplex-Bench v3 真实不流畅口语与倒吸气基准核心定位：真实人类口语缺陷与倒吸气特征对抗评测体系。核心测什么：注入打断前置 60~120ms 的急促倒吸气声（Inhalation Breath Sound），以及口吃与自我修正（‘不是不是...我是说换王老师’）。我们怎么用：检验声学前端能否在话轮真正开启前 50ms 提前压麦 (Pre-emptive Duck-down)，并断言语义状态栈具备否定词忽略能力，杜绝脏参数写入。
【方案 7】 τ-Voice 与 Big-Bench Audio 工具调用基准核心定位：大型语音多轮长任务达成率与口语理解基准。核心测什么：测试模型在口语交流中边聊边调用 API 工具的成功率 (Tool Calling Success Rate)，以及长对话的跨语种理解跟踪能力。我们怎么用：用来验证全双工智能体前后台协同架构中，后台耗时工具执行完后在对话自然气隙中主动带回结果的成功率。
【方案 8】 SIPp + Asterisk 话务电信级压测框架核心定位：电信级话务双向流压测与回声测试框架。核心测什么：高并发实时通话压测，以及硬件扬声器回声泄漏压力测试。我们怎么用：借鉴它的做法，在测试沙盒专门配备‘AEC 回声回灌’功能（支持 0~300ms 可调延迟与 0~1 增益反灌），专门用于寻找硬件自激死锁阈值。
5.2 第三方优秀机制吸收落地说明
• 1. 吸收 LiveKit 队列物理清空策略当检测到用户发声瞬间，客户端 AudioContext 与服务端队列同步执行 purge，杜绝残存半个字破音。
• 2. 吸收 Instruct-FD 音素对齐注水通过 MFA 强制音素对齐，将注入点严格锚定至毫秒级音素切片，实现 100% 确定性复现。
• 3. 吸收 FireRedChat 碰撞窗口分级严格区分无害交叠 (≤150ms) 与恶性碰撞 (>250ms)，模型主动让步率锁定 ≥ 98%。
• 4. 吸收 FDB-v3 倒吸气与口吃对抗前置注入 80ms 倒吸气声与否定纠偏，检验声学提前压麦与上下文语义净化。
• 5. 吸收电信级 AEC 回声注入对抗在沙盒中提供调延迟与增益反灌，检验自激自打断容忍度。

6. 双轨测试流程设计：30分钟基线与 8 大进阶对抗矩阵
6.1 黄金准入基线：30 分钟 6 阶段时序规范
• 阶段 1: 主线长篇讲解 (前 3 分钟) ➔让模型长篇大论讲解方案，测流式下发顺畅度，首音延迟在 600ms 内，生成速度比说话语速快 2.5 倍以上 (RTF < 0.4)。
• 阶段 2: 突然打断并改要求 (第 3 分钟) ➔在第 1.5 秒突然插话‘换李老师负责并查天气’，测模型能不能在 300ms 内刹车闭嘴，并且把变量写入上下文。
• 阶段 3: 多人热烈讨论·静默期 (3~10 分钟) ➔持续推 3 个人吵架的音频 7 分钟，模型必须全场闭嘴当听众，下行推流无可听发射音频。
• 阶段 4: 突然点名发问 (第 10 分钟) ➔吵得最凶的时候突然喊‘系统，刚吵什么？换谁了？’，测模型能不能在 600ms 内唤醒，并准确答出李老师和争论点。
• 阶段 5: 接回之前的话题 (10~15 分钟) ➔让模型‘接着刚才第 3 分钟没讲完的继续说’，看它能不能精准接上断点，通过打断不变性（语义等价）验证。
• 阶段 6: 长时间抗疲劳巡检 (15~30 分钟) ➔反复交替注入附和、思考停顿和扬声器回音回灌，连续跑满 30 分钟，检查 WebRTC 丢包率 < 0.05% 和内存无泄漏漂移。
6.2 全双工 8 大对抗场景超细节实操规约
场景 1：多层嵌套与连续二次打断 (Nested Barge-in) 时延 ≤ 350ms 注入时机：模型刚回复支线第 800ms 处注入‘等等，查上海不是北京！’ (-14dBFS)。底层流转：销毁 Stack[1] 并创建 Stack[1']，更新地名为上海，主线保持挂起。断言门禁：二次刹车 ≤ 350ms，最终回答上海天气，绝不混淆两地。
场景 2：真实不流畅口语与倒吸气耐受 (Disfluent Speech & Inhalation) 误抢 ≤ 1.5% 注入时机：前置注入 80ms 急促倒吸气声，紧接注入‘不是不是...呃...那个...我是说换王老师’。底层流转：声学检测到倒吸气提前 50ms 压麦，语义慢通道过滤否定词‘不是不是’。断言门禁：思考期间发声为 0，精准捕获王老师，无害交叠 ≤ 150ms，误抢话率 ≤ 1.5%。
场景 3：主线显式废弃与断点销毁 (Topic Abandonment & Stack Drop) 幽灵回溯 0% 注入时机：模型播报中途突然插话：‘算了前面说的全作废，直接聊招聘’。底层流转：识别废弃意图，调用 stack.drop_all() 销毁已挂起架构方案栈帧。断言门禁：顺畅进入招聘议题，此后无论多轮对话绝不机械回溯旧方案，幽灵回溯率 0%。
场景 4：高频微弱附和与无缝倾听 (Backchanneling vs Hard Barge-in) 成功率 ≥ 98.5% 注入时机：模型连续播报中以 10 秒间隔穿插‘嗯/对/好的’ (≤ 350ms, -22dBFS)。底层流转：轻量分类器 60ms 判定为倾听反馈，不发 CANCEL 信令，保持 Opus 连续解码。断言门禁：附和成功率 ≥ 98.5%，下行音频无截断顿挫，播放抖动 ≤ 5ms。
场景 5：声纹排他与多人讨论拒识 (Voiceprint Diarization) 下行 0 字节 注入时机：主麦克风混入背景 2 人争吵音频 (SNR 5dB，基频与主用户存在明显差异)。底层流转：提取说话人声纹向量与绑定用户比对，低于阈值激活静音门禁。断言门禁：旁人争吵期间下行推流增量严格为 0 字节，误插话次数严格为 0 次。
场景 6：紧急安全与情绪突变刹车 (Urgent Safety & Emotion Interrupt) 时延 ≤ 150ms 注入时机：注入急促高分贝音频：‘快停下！别说了！’ (-6dBFS, 语速 > 300字/分)。底层流转：声学与情感特征探针触发最高优先级 Emergency 中断，跳过慢语义直达静音。断言门禁：刹车时延 ≤ 150ms，下行队列 1 帧内清空，后续自适应切换安抚音色。
场景 7：弱网抖动下的播放缓冲清空 (Buffer Purge Under Network Stress) 残存 ≤ 20ms 注入时机：注入 15% 丢包与 150ms 抖动，在模型发声中途触发打断。底层流转：服务端发送 CANCEL，端侧 WebRTC 原生清空 AudioContext 播放未消费缓冲。断言门禁：扬声器残存音频持续时间 ≤ 20ms (≤ 1 帧)，彻底杜绝‘人喊停后 AI 还在机械播 1 秒’。
场景 8：长程高频疲劳与状态栈健康 (Context Stack Fatigue & Memory Leak) 内存漂移 ≤ 10% 注入时机：在 30 分钟会话内以随机时间间隔注入 15 次打断、7 次支线与 20 次附和。底层流转：实时监控 RSS 内存分配、WebRTC 句柄数与 Token 长度，验证压缩滑动窗口。断言门禁：前后端内存漂移量 ≤ 10%，WebRTC 零死音，全过程无 OOM 与延迟劣化。

7. 怎么防止测试语料自己带坑？（前置标定与方言矩阵）
测试用的音频必须本身是干净的。我们建立了语料工场，所有测试音频入库前必须先过一次标准 ASR 校验，普通话基准样本字错率必须为 CER = 0.0% 才能算合格用例。
• 7.1 方言与口音对抗覆盖平翘舌不分、鼻边音不分（如‘你老师’和‘李老师’）、粤普前后鼻音弱化、北方快语速儿化音、江浙吴语调。
• 7.2 极端说话语速与声线覆盖 1.5 倍速着急抢话连读、0.7 倍速结结巴巴犹豫、儿童高音调（防高频误过滤）、老年人低沉沙哑声。
• 7.3 恶意谐音同音挑衅在多人讨论里故意高频说‘模式设计’、‘摸索前进’、‘魔术表演’、‘磨合期’，测模型会不会误把这些词当成‘小模’误唤醒，误触发必须为 0.0%。

8. 对话断点状态栈四态仲裁模型 (Context Resume Engine)
为彻底规避打断后‘无脑回溯’导致的逻辑灾难，状态机确立四态决策仲裁机制：
[用户输入 / 打断意图]
    │
    ├── ① 明确要求接续 ("接着刚才的说") ──► [Resume Full] 从中断点恢复上下文流式输出
    ├── ② 显式要求作废 ("前面说的不用了") ─► [Drop Stale] 物理销毁已挂起栈帧 (Pop & Drop)
    ├── ③ 追加修改约束 ("预算改5万重新规划") ► [Merge Context] 增量重构主线状态 (State Rebase)
    └── ④ 超过 10 轮未召回 (TTL 窗口耗尽) ──► [Timeout Expire] 自动退火归档防长程幻觉
① 完全接续 (Resume Full)用户明确表示接续时，弹出栈顶快照，保持‘打断不变性’（语义等价度评分 ≥ 95%）。
② 彻底丢弃 (Drop Stale)用户指示作废时，标记为 Tombstone 墓碑，物理释放上下文 Token，禁止幽灵复活。
③ 条件合并 (Merge Context)最贴近人类思维的高阶形态。打断中的新参数与主线上下文动态合并（Rebase），发起新规划。
④ 超时淘汰 (Timeout Expire)为挂起栈帧设立 TTL（默认 10 轮）。支线若长期未召回，自动衰减归档，避免长程污染。

  - 测试场景: 模型长句主线播报中，每隔 8~12 秒周期性注入 150ms~300ms 微弱附和语素（“嗯”、“对”、“好的”，能量 -20 ~ -25dBFS）。

• 用例 B：人类思考留白阶梯停顿对抗 (Hesitation Ladder Resistance)
  - 测试场景: 模拟人类犹豫停顿，在话轮中设置 500ms、1000ms、1500ms、2000ms、2500ms、3000ms 六阶静音梯次，前置伴随“呃...”、“让我想想...”弱能量短语。

• 用例 C：边聊边调工具并发抗撕裂断言 (Concurrent Tool Calling Audio Jitter)
  - 测试场景: AI 持续推流播报主线方案时，后台异步触发天气/数据库等工具查询（耗时 1~2s）。
  - 核心断言: WebRTC getStats() 实测 P95 Jitter ≤ 12ms，Max Jitter ≤ 15ms，Packet Loss Rate == 0.00%，客户端缓冲区饥饿 Underrun 次数为 0，瞬态首包延迟增量 Delta TTFT ≤ 50ms。

• 用例 D：短时脉冲杂音抗扰断言 (Impulse Noise Rejection: 咳嗽/喷麦/敲桌)
  - 测试场景: 注入 50ms ~ 120ms 高能量冲击杂音（能量 > -10dBFS，但非人声持续共振峰结构）。
  - 核心断言: 误打断次数 False Barge-in == 0 次，严禁触发 CANCEL/FLUSH 信令；快通道压麦 Duck-down 触发后，慢通道 ≤ 100ms 识别非人声并于 ≤ 80ms 内音量平滑无感回弹至 100%。

# 10. 全双工语音交互端到端质量评估体系 (v1.5.0 协议与评测基准补全版)

## 10.1 核心认知厘清：全双工、定向唤醒与声学前端的边界解耦
在工程实践中，必须严格区分模型能力与端侧声学硬件能力，严禁将多项能力混为一谈：
- **语义打断 (Semantic Barge-in)**: AI 播报中途，用户插入新意图，模型服务端判定是否截断并切换上下文。
- **多人对话倾听与拒识 (Diarization & Noise Rejection)**: 两人同时说话或旁人闲聊时，模型利用语义上下文或声纹向量判断是否属于目标意图。
- **定向唤醒与声源定位 (DOA & Beamforming)**: 依赖端侧多麦克风阵列与硬件前端，纯云端 WebSocket 接口仅能测试混音后的语义拒识，无法证明物理声源定位能力。
- **离线唤醒词检测 (KWS)**: 本地轻量模型待机触发（如“你好助手”），属于系统准入门禁，不属于全双工多轮对话模型自身能力。

## 10.2 WebSocket 实时流接口必须守住的 4 大协议细节
1. **持续双向流推流 (Continuous Audio Ingestion)**:
   - 上行强制采用 16kHz、单声道、PCM S16LE；
   - 模型下行播放期间麦克风必须保持全时收音，严禁在 AI 发声时关闭采集；
   - 用户停止说话后必须持续发送静音帧填充，维持长连接心跳与模型上下文。
2. **打断状态机与本地播放队列彻底清空 (Queue Flush)**:
   - 收到 `response.interrupted` 时，必须核验对应 `run_id` 与 `turn_id` 的回复已闭环；
   - 客户端 AudioContext 待播队列必须物理清空（Flush），严禁将未播放的废弃音频残留播放出来。
3. **真实听感时延四段解耦 (Perceptual Latency Decoupling)**:
   - **TTFT (首字生成时延)**: 用户发声结束到首个文本/事件包。
   - **First Audio Chunk (首音频包时延)**: 收到首个 PCM 语音切片时间。
   - **EOT-to-Speech (扬声器物理出声时延)**: 从用户话毕到扬声器真实震动发声时间。
   - **Barge-in Stop Latency (打断刹车时延)**: 用户插话起始点到扬声器彻底静音时间。
4. **播放回执真实进度对齐 (Playback Progress Acknowledgment)**:
   - `playback.chunk.completed` 和 `playback.completed` 必须按实际扬声器物理消耗进度发送，严禁测试客户端提前假确认，确保服务端会话状态机与听感绝对一致。

## 10.3 吸收融合的业界 5 大标杆开源基准
- **Full-Duplex-Bench (FDB v1~v3)**: 引入口语停顿、填充词、自我修正对抗用例，采纳打断不变性（Interruption Invariance）语义等价评分。
- **ServiceNow EVA**: 引入双语音 Agent 对弈模型（Virtual User Agent 动态对抗被测 Agent），并引入确定性工具执行器与物理状态真实闭环核验。
- **voice-agent-barge-in-tests**: 规范重叠说话、回声自激与打断刹车毫秒级自动化测量工具。
- **voice-evals**: 自动化生成带时间戳、波形切片与事件轴的交互测试报告，作为 CI 质量门禁。
- **OpenMOSS / MOSS-Live 协议基准**: 官方 WebSocket 长连接与实时事件驱动。

## 10.4 全双工自动化质量评估核心 SLA 门禁
- **打断成功率 (Barge-in Success Rate)**: ≥ 98.0%
- **打断刹车时延 (Barge-in Stop Latency)**: P50 ≤ 200ms, P95 ≤ 300ms, MAX ≤ 350ms
- **附和免打断率 (Backchannel Precision)**: ≥ 98.5%
- **思考停顿误抢率 (Premature Interruption Rate)**: ≤ 1.5% (容忍窗口 0.5s ~ 2.5s)
- **待播队列残留 (Buffer Underrun & Leakage)**: 队列严格清空 (Queue Size = 0)，残留音频 ≤ 1 帧 (≤ 20ms)
- **双 Agent 对弈任务物理闭环率**: 100%（杜绝 Agent 口头答应但后台未执行的假完工）
